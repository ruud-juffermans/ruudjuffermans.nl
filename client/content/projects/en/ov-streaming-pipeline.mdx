*Own project. This is the reading version; the project page itself shows the same content with the diagrams and screenshots.*

Two files on an open endpoint contain, every minute, where roughly 4,900 vehicles are and how late they are. Turning that into a dashboard is an afternoon's work. Turning it into figures that keep coming 24 hours a day, are still right after a crash, don't silently lose broken records, and let you recompute an hour from the past — that is a different project.

This is that second project. Fixed definitions for the delay figures, stored per window in Postgres, with a live Streamlit dashboard on top and a Grafana dashboard that shows the state of the data supply. Underneath runs a streaming pipeline on Kafka with a raw archive you can recompute from. Thirteen containers, `make up`, no accounts and no keys.

**In short:** Postgres · Streamlit + pydeck · Prometheus + Grafana · Python 3.12 · Kafka (Redpanda) · MinIO · Docker Compose — 106 unit tests, ruff clean — runs entirely locally, zero cost.

## Why this project

Putting a delay figure on a dashboard is the easy part. The interesting things only happen once real time is involved: measurements arriving late, a process falling over between two writes, a feed that doesn't follow its own documentation. Each of those can make a figure wrong without the dashboard looking any different.

I wanted to run into those things instead of reading about them. A nationwide, public, always-on data source forces that — and produces something you can show at the same time.

## What is measured

The delay comes from the trip predictions in the feed; the vehicle positions themselves carry no delay. Those delays are summarised in fixed five-minute windows over four dimensions at once: line, stop, operator and network. Each window has five figures: the number of observations, the mean, the exact P90, the maximum and the minimum.

Every closed window is one row in Postgres, in the table `delay_aggregates`, keyed on `(window_start, dimension, dimension_id)`. The dashboard reads that table, and the same figures per line, stop, operator or network can be queried with plain SQL.

Four choices in the definition:

**Exact P90 instead of an estimate.** With a few thousand observations per window per key, an exact calculation (nearest-rank) costs nothing, and it makes a test against a window computed by hand possible. At real scale this is the part you'd replace, for instance with a t-digest.

**Each dimension separately, not derived.** You can't derive the network P90 from the per-line P90s. So the four dimensions are each tracked separately.

**A standing delay keeps counting.** Only changes relative to the previous measurement are passed on. To stop a train that has been sitting at +5:00 for twenty minutes from disappearing from the statistics, a heartbeat goes out every sixty seconds.

**What "late" means.** A window is settled exactly once. Anything more than two minutes behind no longer counts towards it, but is counted as late. In practice that number is zero, because the time of a measurement is the feed's own generation time and it only increases.

## The dashboards

The live dashboard, built in Streamlit, reads straight from Postgres. At the top are six KPI tiles for the last closed window: vehicles live, trips with a prediction, mean delay, P90, percentage on time and the worst line. Below that, the map with every vehicle position and that window's worst lines.

The detail panels show network delay over the last three hours in five-minute windows, mean delay per operator and the distribution of current delay across active trips. At the bottom is a health strip with the figures about the data supply itself: messages per second in and processed, backlog, late events and records set aside per hour.

The Grafana dashboard goes one level deeper, with 26 panels: throughput, backlog and processing time, correctness (records set aside, late events, windows) and state and archive.

## What the data really looks like

The feed doesn't follow its own documentation. Entity ids like `2026-09-06:GVB:13:13605` contain the operator code, which appears nowhere else in the message, so it's taken from the id. Ghost vehicles roam the feed: a bus "STOPPED_AT" the same spot for eleven days, and one vehicle reporting from 29 minutes in the future. Positions older than ten minutes or more than a minute ahead are dropped. All of those cases are captured in recorded feed files in the repo: 140 KB that pins every parser test to reality.

Rush hour and night differ by a factor of a hundred: at half past eleven at night it's 50 to 110 messages per second and 1,400 vehicles, at four in the morning two messages per second and twenty buses — and the dashboard says so honestly instead of faking movement. Between 01:00 and 05:00 there are twenty to thirty night buses running. Without intervention the last window is never settled, because no measurement arrives to push time forward; so after ninety seconds of silence the processing moves on by the wall clock.

A sleeping laptop is not an outage, but looks exactly like one in Grafana: macOS wakes up for 45 seconds of maintenance every hour, which produces one tall spike per hour and a watermark lag of half an hour. `make keep-awake` is in the runbook now.

Broken records are set aside, not lost. Anything unreadable goes to a separate queue (dead-letter queue) with the original bytes and the reason for the error, and doesn't block the rest. The feed sends the same broken entity again every minute, so each combination of entity and reason is set aside once. Within ten seconds such a record shows on the Grafana panel and in the health strip; after a fix it can be offered again.

## Twice, a figure was silently wrong

Both times good measurements were labelled "late" and dropped, so windows rested on fewer observations than there were. The concept behind it is the watermark: the clock that says how far the data has got, and therefore which windows may close. Late events don't vanish quietly: they are counted, and that counter is on the Grafana dashboard and in the health strip.

**169,000 events gone after a catch-up.** The first version had one clock for everything: the newest measurement received. That worked fine until a forty-minute catch-up came along. The stream's six partitions were read at different speeds, the fastest pulled the clock ahead, and 169,000 perfectly normal events from the slower partitions counted as late. Now every partition has its own clock and the slowest one rules; a partition that sends nothing for 120 seconds is left out, otherwise no window would ever close again.

**130,000 events gone because of a clock in the future.** At startup the clock is set to the last window already in Postgres, so that redelivered messages don't write a partial window over a complete one. Once, a recomputation that was still running set that clock into the future, after which 130,000 good events were dropped. Since then that starting value is capped at the wall clock.

## Why the figures hold

**Reprocessing doesn't double count.** A window is written to Postgres first; only then is it recorded how far the stream has been read. If the process dies in between, the same messages come in again, the same window is recomputed from the same events and written under the same key. The row is replaced; nothing is added to it. `test_duplicate_delivery_does_not_double_count_in_real_postgres` applies the same window twice against the real database and checks that there is one row, with the original count.

**A time range can be recomputed.** All raw messages also go to an archive. `make replay FROM=… TO=…` recomputes a time range from it, through the same code as the live processing: there is no second version of the calculation rules. Measured: 122,364 archived messages from twelve minutes of morning rush, recomputed into 11,323 windows in about ten seconds.

**Tested against a hand-computed window.** `make test` runs 106 unit tests without infrastructure, including the parser against recorded feeds (one of mixed quality and one of pure nonsense among them), a window computed by hand and the dashboard's SQL invariants. The integration tests run the dashboard queries and the duplicate-delivery test against real Postgres.

## How it works underneath

A producer fetches the two feeds and publishes them to Kafka (Redpanda). Two independent consumers read along: one computes the windows and writes to Postgres, the other writes the raw bytes to the archive in MinIO. If the archive is briefly gone, the figures keep coming, and the other way round. A sidecar loads the static GTFS reference data daily into staging tables that are swapped in a single transaction, so readers never see a half-loaded set.

**Only changes are passed on.** The feed sends the complete picture again every minute; passing that on directly gives around 700 messages per second that are mostly repetition. So each measurement is compared with the previous one. In the morning rush about 45% drops out that way: five to twenty times fewer messages, with identical window figures.

**The archive keeps raw bytes.** Kafka is a 24-hour buffer here, not an archive. What you still need a month from now lives in MinIO, unprocessed. That lets you run a new reading rule over it later; had I stored the already interpreted data, that day's interpretation would have been frozen forever.

**A new message format breaks nothing.** Every message carries a version number, and the processing reads the current and the previous version, so both sides can be updated independently. An unknown version doesn't crash but is set aside, like any other unreadable record.
