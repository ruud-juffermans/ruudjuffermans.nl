*Own project, built to show how I work. Everything described here is real and verifiable in the repo.*

## Why this project

You don't judge a report by the dashboard, but by what sits underneath: is the grain right, are the definitions pinned down, do errors get caught before they reach a report. This project records those choices in the open, on data anyone can check.

Two public sources, both queryable without an API key:

- **RDW open data** — registered vehicles, fuel, observed defects and defect codes: record-level transaction facts
- **CBS StatLine** — the motor-vehicle fleet per municipality and the municipal boundaries per year: a periodic snapshot plus the municipality dimension

The combination is deliberate. Two facts with a different grain in one schema is exactly what dimensional modelling is about — and exactly where it goes wrong when the grain isn't made explicit.

## The questions the report answers

The Power BI report answers three questions, directly on the star schema:

- The vehicle fleet per municipality and reference year, including redivided municipalities
- The top defects per vehicle type and build year, with a slicer on energy source
- How the RDW sample lines up with the fleet CBS reports per municipality

## The star schema

Two facts, five dimensions and one bridge. Every fact table states its **grain** explicitly: one sentence, no room for interpretation.

| Fact table | One row per… | Type |
| --- | --- | --- |
| `fct_gebrek_constatering` | observed defect per inspection per vehicle | transaction |
| `fct_voertuigpark_gemeente` | municipality per reference year per vehicle type | periodic snapshot |

With dimensions for date (generated, including Dutch public holidays), municipality, vehicle, fuel and defect. The date dimension is the conformed dimension both facts share.

## Design choices

- **Why this grain.** `fct_gebrek_constatering` sits at one observed defect per inspection per vehicle, so counting defects is simply `count(*)`. The source column with the inspection total is deliberately left out: it repeats the same number on every row, and a `sum()` over it double counts.
- **Why a bridge.** 12,671 vehicles have more than one fuel. Without a bridge table you count those twice as soon as someone filters on energy source.
- **Why SCD type 2 on municipality.** The Netherlands went from 393 municipalities in 2015 to 342 in 2026. Without history, past figures shift retroactively — a silent error in management information. The fact joins on municipality code and reference date within the validity period; three custom tests guard that the periods are contiguous, don't overlap and have at most one current version.
- **What couldn't be done.** The intended grain of municipality × fuel type doesn't exist at CBS: the fuel split doesn't go below province. It became municipality × vehicle type, and that choice is written out in the repo.

## Power BI

The semantic model mirrors the schema and doesn't repair it. Relationships run 1:* from dimension to fact with a single-direction cross filter, the SCD2 dimension hangs off the fact via the surrogate key, the bridge is set up as many-to-many with one bidirectional cross filter, and the DAX measures are cross-checked with `dbt show`. A report that bypasses the model is a second model — and then you have two truths.

## Data quality

The dbt tests cover `unique` and `not_null` on every key, `relationships` from every foreign key to its dimension, `accepted_values` on reference columns, plus custom tests on the grain: no duplicate rows per grain definition. They run on every pull request, together with `dbt build` and the linters.

Those tests also caught a dataset that looks fine and is wrong. The default run works with a sample from the RDW sets (about 58 million rows together). Taking the first 500,000 rows of each set yields three different vehicle populations, so facts point at dimension rows that aren't in the snapshot. The fix is one licence-plate range, determined on the vehicles set and reused for every other set. Result: zero orphan rows in fuel and defects, and all 622 defect codes in use present in the code list.

This is the same way of working I bring to any team: definitions and transformations pinned down, with a test at every step, so an error surfaces before anyone steers on the number.
